# Nova 后端开发学习教程（给前端同学的 NestJS 入门）

> 面向读者：会 Vue3 + TypeScript，想看懂、敢改、能加需求的 `nove-admin-nest` 后端。
> 学完目标：① 能讲清楚一次登录背后发生了什么；② 能独立加一个 CRUD 模块；③ 能自己排查“会话过期 / 权限不足 / 404”三类报错。
> 约定：文中文件路径都以 `nove-admin-nest/src` 为根，特别标注的除外。

---

## 第 0 章 技术栈全景（先建立地图）

| 技术 | 一句话 | 前端类比 | 在本项目里的职责 |
|---|---|---|---|
| NestJS | Node.js 的企业级后端框架，强约定、装饰器驱动 | 像“后端的 Vue + Spring 思想”：模块化组织代码 | 所有业务代码的骨架 |
| TypeORM | 用 TS 类来操作数据库（ORM） | 像 Pinia + 持久化：类即表结构 | 实体定义、查询、关联 |
| PostgreSQL | 关系型数据库，端口 5432，库名 `nova2` | 就是 MySQL 的亲戚，语法大同小异 | 存用户/角色/菜单/字典等一切业务数据 |
| Redis | 内存键值数据库，端口 6379 | 像装在服务端的 `localStorage`，但有过期时间 | 存登录会话（token → 用户信息） |
| JWT | 自包含的登录票据（一串三段式字符串） | 像 Cookie，但服务端不存、靠签名验真伪 | `accessToken`，载荷里只有 `userId` |
| class-validator | 用装饰器给 DTO 加校验规则 | 像 naive-ui 的 `rules`，但是写在后端接口入参上 | 用户名长度、密码必填等 |
| Winston | 日志库 | `console.log` 的生产版（分级、落盘） | 后端黑窗口里 `[Nova] ... LOG` 都是它打的 |
| Swagger | 接口文档自动生成 | 后端自带的“接口版 Storybook” | http://localhost:3001/api-docs，可直接点点点调接口 |

服务与端口（本地）：PG 5432 → 后端 3001 → 前端 9980。前端调后端走 `http://主机名:3001`（`src/service/http/index.ts` 里按页面主机名自动拼，局域网联调才不断）。

## 第 1 章 项目结构漫游

```
src
├── main.ts                  # 入口：建应用、挂中间件、监听 3001（= 前端的 main.ts + App.vue 二合一）
├── app.module.ts            # 根模块：组装所有子模块 + 注册全局守卫/拦截器/过滤器/管道
├── config/                  # 配置中心（dev.ts / prod.ts，按 NODE_ENV 切换）
├── common/                  # 全局基础设施
│   ├── decorators/          # 自定义装饰器：@Public、@RequirePermissions
│   ├── dto/                 # 通用 DTO：SearchQuery（pageNum/pageSize）
│   ├── enums/               # 枚举：ApiErrorCode、DataScope、RedisKey
│   ├── filters/             # 异常过滤器：ApiException 长什么样由它定
│   ├── guards/              # 守卫：JwtGuard（验票）、AuthGuard（验权限）
│   └── interceptors/        # 拦截器：GlobalInterceptor（统一包返回体 + 打日志）
├── modules/
│   ├── auth/                # 登录/登出/用户信息/菜单（你最该先读的模块）
│   ├── system/              # user / role / menu / dept / dict 五个业务模块
│   ├── monitor/             # login-log / server（登录日志、服务状态）
│   └── common/redis/        # Redis 封装
├── types/                   # 全局类型：Session（会话长啥样就看它）
└── utils/                   # 工具：crypto（sha256）、convert、tree、captcha
```

**一个业务模块的标准五件套**（以 `system/user` 为例，前后端对照着看）：

| 文件 | 作用 | 前端对照物 |
|---|---|---|
| `user.controller.ts` | 收 HTTP 请求：路径、方法、参数从哪取 | vue-router 的路由表 + 页面里的 `fetchXxx` 调用点 |
| `dto/create-user.dto.ts` | 入参形状 + 校验规则 | `Entity.User` 类型 + `rules` 校验 |
| `entities/user.entity.ts` | 数据库表结构（类即表） | 后端独有，前端没有对应物 |
| `user.service.ts` | 真正干活：查库、加密、组装 | `service/api/*.ts` + pinia action 的合体 |
| `user.module.ts` | 把上面四个注册到 Nest 容器 | `app.use(router)` / `app.use(pinia)` 那类装配代码 |

> 前端思维转换第一课：**Controller 只做“接电话、递话筒”**（取参、调 service、返回），**禁止在 Controller 里写 SQL 或业务判断**；Service 里禁止直接碰 `req/res`。这个分层习惯养成了，后端代码就永远好读。

## 第 2 章 一个请求的一生（以 POST /login 为例）

```
浏览器 alova                    NestJS 后端
   │                                │
   │  POST /login                   │  main.ts：NestFactory.create(AppModule, { cors: true })
   │  {userName,password}           │  注册：ValidationPipe / JwtGuard / AuthGuard / GlobalInterceptor / Filter
   │ ──────────────────────────────▶│
   │                                │  ① JwtGuard：@Public()？是→直接放行（不查 token）
   │                                │  ② AuthGuard：无权限要求→放行
   │                                │  ③ ValidationPipe：按 LoginAuthDto 校验入参（密码长度不够直接 400）
   │                                │  ④ AuthController.login()：取 Body + ClientInfo（IP/浏览器/系统）
   │                                │  ⑤ AuthService.login()：validateUser → 记登录日志 → 生成 token → 存 Redis
   │                                │  ⑥ GlobalInterceptor：包成 { code:200, data, message:'操作成功' } + 打印一行日志
   │  ◀──────────────────────────────
   │  { code:200, data:{accessToken,role}, message }
```

对照你熟悉的 alova 拦截器：

| 后端环节 | 前端对应 | 一句话 |
|---|---|---|
| Guard（守卫） | 路由守卫 `beforeEach` | 进门前查证件，不合格直接拦，根本到不了业务代码 |
| Pipe（管道） | 表单 `validate` | 入参自动校验 + 类型转换，不合格 400 |
| Interceptor（拦截器） | alova 的 `beforeRequest` / `responded` | 包统一返回体、打日志、管超时（30s） |
| Filter（过滤器） | 响应错误分支 `handleBusinessError` | 把抛出的异常翻译成前端能读的 `{code,message}` |
| Decorator（装饰器） | `defineProps` / 路由 `meta` | 贴在类/方法上的“备注”，框架读备注干活 |

**必须背下来的返回体**（`common/interceptors/global.interceptor.ts`）：

```json
{ "code": 200, "data": "真实数据", "message": "操作成功" }
```

注意这个巨坑：**HTTP 状态永远 200，哪怕是业务报错**（`ApiException` 默认 `HttpStatus.OK`）！前端只能看 `code` 字段：`200`=成功，`500`=业务失败（“用户不存在”“权限不足”都是 500 + message 区分）。401 只在“没带 token / 会话没了”时出现。所以你在 Network 里看到 200 先别开心，点开看 `code`。

## 第 3 章 NestJS 核心四件套 + 依赖注入（DI）

```ts
// 1. Controller：只管“接请求”（modules/system/user/user.controller.ts）
@Controller('user')              // 类上的路径前缀 → 所有接口都是 /user 开头
export class UserController {
  constructor(private readonly userService: UserService) {}  // ← 这就是依赖注入

  @Post()                        // POST /user
  @HttpCode(200)
  @RequirePermissions('system:user:add')  // 进门条件：会话里要有这个权限码
  create(@Body() createUserDto: CreateUserDto) {  // @Body() = 取请求体
    return this.userService.create(createUserDto)
  }

  @Get(':id')                    // GET /user/123，:id 是路径参数
  findOne(@Param('id') id: string) { ... }

  @Get()                         // GET /user?pageNum=1&pageSize=10
  findAll(@Query() searchQuery: SearchQuery) { ... }  // @Query() = 取 ? 后面的参数
}
```

```ts
// 2. Module：装配工（user.module.ts 思想示意）
@Module({
  controllers: [UserController],
  providers: [UserService],                       // Service 在这里“登记”，才能被注入
  imports: [TypeOrmModule.forFeature([User])],    // 顺手把 User 表的 Repository 也登记了
})
export class UserModule {}
```

**依赖注入一句话**：`constructor(private readonly userService: UserService)` 里声明“我要用 UserService”，Nest 启动时自动 new 好塞进来。你不需要手动 `new`，也不需要 import 实例——这是 Nest 和 Vue 的 `provide/inject` 同一个思想，只是发生在服务端启动时。

**装饰器速查表**（看到能认出来就行）：

| 装饰器 | 贴在哪 | 干嘛 |
|---|---|---|
| `@Controller('user')` / `@Get() @Post() @Patch() @Delete()` | 类 / 方法 | 声明路由，相当于前端路由表 + method |
| `@Body() @Query() @Param() @Headers()` | 方法参数 | 从请求体 / ?参数 / 路径 / 请求头取值，相当于 `route.query` |
| `@Public()` | 方法 | “此接口免登录”（登录、验证码）。**血泪教训：绝不能和 @RequirePermissions 贴在同一个方法上**，否则 JwtGuard 跳过导致会话为空，权限守卫必炸“会话已过期”（我们真踩过，POST /user 瘫过一次） |
| `@RequirePermissions('system:user:add')` | 方法 | 进门条件，见第 4 章 |
| `@ApiOperation/@ApiTags` | 方法 / 类 | 只给 Swagger 文档看的，不影响运行 |
| `@Injectable()` | Service 类 | “我可以被注入”，不写就塞不进 constructor |

## 第 4 章 登录鉴权全链路（本章最重要）

### 4.1 登录：POST /login（`modules/auth/auth.service.ts`）

```ts
async login(loginAuthDto, clientInfo) {
  const username = loginAuthDto.username || loginAuthDto.userName  // 兼容前端大写 N
  // 1. 验用户：按用户名查库 → sha256(password) 对比
  const user = await this.validateUser(username, password)
  // 2. 记日志：成功/失败都写 sys_login_log（登录日志页的数据就从这来）
  // 3. 发票据：
  const token = await this.generateTokenAndStoreSession(user, clientInfo)
  return token  // → { accessToken, role: ['admin'] }
}

generateToken(user) {
  // JWT 载荷里只有 userId，有效期 7d（config 里配的），密钥也在 config
  return { accessToken: this.jwtService.sign({ userId: user.id }) }
}

async generateTokenAndStoreSession(user, clientInfo) {
  const token = this.generateToken(user)
  const [permissions, roles] = await Promise.all([...])  // 查出该用户全部权限码+角色
  // 会话存 Redis：key = 'user_token:' + accessToken，过期 7 天
  await this.redisService.set(sessionKey, { ...user, ...clientInfo, permissions, roles }, 604800)
  return token
}
```

记住三件事：① 密码存的是 sha256 hex（种子 admin/123456 的哈希是 `8d969eef...`）；② token 本身不含角色，前端要的 `role` 是登录接口**顺手查好一起返回**的；③ 真正的权限判定依据是 Redis 里的会话，不是 token。

### 4.2 双守卫：每次鉴权请求都要过两道门

```ts
// JwtGuard（common/guards/jwt.guard.ts）：查“票真不真”
@Public() 的直接放行；
否则从 Authorization: Bearer xxx 取 token → 验签名 → 按 token 到 Redis 取会话 →
  取不到报「用户会话已过期或不存在」(401)；取到了挂到 request.session 上。

// AuthGuard（common/guards/auth.guard.ts）：查“够不够格”
方法上没写 @RequirePermissions/@RequireRoles → 直接放行；
写了 → 从 request.session 里拿 permissions/roles 对：
  - 角色里有 roleKey === 'admin' 的是超管，直通（这就是 admin 啥都不缺的原因）
  - 否则必须同时满足权限码 → 不满足报「权限不足」
```

对照前端：`JwtGuard ≈ beforeEach 里判有没有 token`，`AuthGuard ≈ hasPermission() 判角色`。只不过后端这两道门是**全局**的（`app.module.ts` 里两个 `APP_GUARD`），每个接口默认都要过，除非贴了 `@Public()`。

### 4.3 登出与“踢人”原理

`logout(token)` 就是 `redis.del('user_token:' + token)`——会话一删，这个 token 立刻作废。想做“强制下线/单点登录顶号”，思路一模一样：删 Redis 里的会话键。

## 第 5 章 数据库 TypeORM（把类当表用）

```ts
// modules/system/user/entities/user.entity.ts（节选）
@Entity('sys_user')                      // ← 类名 User 对应表 sys_user
export class User {
  @PrimaryGeneratedColumn() id: number   // 自增主键

  @Column({ length: 30 })
  username: string                       // 驼峰属性名…

  @ManyToMany(() => Role, role => role.users)
  @JoinTable()
  roles: Role[]                          // …多对多关联：一个用户多个角色
}
```

三件必须知道的事：

1. **命名策略**（`utils/naming-strategy.ts`）：属性 `nickName` 自动对应列 `nick_name`，`deptId` 对应 `dept_id`。所以你在 psql 里看到的全是下划线，代码里全是驼峰——不是两个人写的，是策略转的。
2. **`synchronize: true`（`config/env/dev.ts`）**：启动时按实体**自动建表/补列**，但**绝不删列、不建库**。生产环境必须关掉（否则改个实体就动表结构）。库 `nova2` 是我们手工 `CREATE DATABASE` 的，还记得吗？
3. **自增 id 的坑**：`example.sql` 是带固定 id 导入的，序列（Sequence）还停在 1，下一次自增插入就会主键冲突。我们修过一次：`SELECT setval('sys_user_id_seq', (SELECT MAX(id) FROM sys_user))`。以后每次导种子数据都要顺手校准六张表的序列（user/role/menu/dict_data/dict_type/dept/login_log）。

**分页查询固定套路**（所有列表接口都长这样）：

```ts
// 入参：common/dto/page.dto.ts → SearchQuery { pageNum?, pageSize? }（默认 1 / 10）
// 查询：userRepository.findAndCount({ where, skip, take, order })
// 返回：{ list, total }   ← 注意是 total，不是前端习惯的 count！
```

relations（联表）是按需点的：`findOne({ where: {id}, relations: ['roles', 'roles.menus'] })`，不写 relations 就查不到关联（TypeORM 默认懒，不像你想的那样自动 join）。

## 第 6 章 Redis 在干嘛 + 配置系统

Redis 在本项目就干两件事（`modules/common/redis/redis.service.ts` 只是 ioredis 的薄封装：`set(key, value, 秒)` / `get` / `del`）：

1. **存会话**：`user_token:{accessToken}` → `{用户信息, permissions, roles, IP/浏览器}`，7 天过期。登录写、鉴权读、登出删。
2. **（预留）字典/热点缓存**：`dict/data/refresh` 接口就是留的刷新缓存的口子，目前是空实现——第 12 章练习题有它。

查线上会话：`redis-cli keys 'user_token:*'` 能看到当前所有登录；`TTL 键名` 看剩余过期秒数。

配置系统（`src/config/`）：`app.config.ts` 按 `NODE_ENV` 二选一 `env/dev.ts` / `env/prod.ts`。`pnpm start:dev` 实际跑的是 `cross-env NODE_ENV=dev nest start --watch`。要改端口、JWT 有效期、验证码开关、Redis 地址，认准 `env/dev.ts` 这一个文件。注意和前端 `.env` 是两套：前端管“调谁”，后端管“我是谁”。

## 第 7 章 CRUD 五步法（照着抄就会加模块）

假设要加个“公告管理”（表 sys_notice：id/title/content/status），五步：

1. **实体** `modules/system/notice/entities/notice.entity.ts`：照 `menu.entity.ts` 写 `@Entity('sys_notice')` + 列。重启后端，`synchronize` 会自动建表（去 psql `\d sys_notice` 验证）。
2. **DTO** `dto/create-notice.dto.ts`：`title` 必填（`@IsNotEmpty`）、`content` 可选——对照 `create-user.dto.ts` 抄装饰器。校验不通过前端会收到 400 + 中文 message。
3. **Service**：CRUD 照 `user.service.ts` 的 `create/findAll/update/remove` 骨架写；分页直接抄 `findAndCount` 那十行。
4. **Controller**：`@Controller('notice')` + 五个方法 + `@RequirePermissions('system:notice:xxx')`（权限码先在 `sys_menu` 里加三行按钮权限，再配给角色，菜单管理页能直接看到吗？不能——按钮权限要在角色编辑里勾，前端角色弹窗的菜单树就是干这个的）。
5. **Module**：`notice.module.ts` 登记 Controller/Service/`forFeature([Notice])`，再到 `system.module.ts`（或 app.module）的 imports 里加上。**新手 80% 的“接口 404”都是这一步忘了。**

校验装饰器速查（`class-validator`）：`@IsNotEmpty` 必填、`@IsOptional` 可空、`@IsString/@IsNumber/@IsArray` 类型、`@Length(5,30)` 长度、`@Matches(/^...$/)` 正则、`@IsIn(['male','female'])` 枚举、`@IsEmail()` 邮箱。注意全局 `ValidationPipe` 用的是默认配置：**只校验，不 strip 未定义字段也不自动转型**，所以 query 里的 `pageNum` 是字符串的话要自己 `Number()`（看 `auth.controller.ts` 的 `getUserPage` 就是这么干的）。

## 第 8 章 前后端契约对照表（我们联调时修出来的，背下来）

| 前端要的 | 后端给的 | 翻译层在哪 |
|---|---|---|
| 登录返回含 `role: ['admin']` | `generateTokenAndStoreSession` 顺手查 `findUserRoles` 拼上 | 后端 `auth.service.ts` |
| 用户列表 `{list, count}`，字段 `userName/tel/nickname` | 库里是 `{list, total}`，字段 `username/phone/nick_name` | 后端 `GET /userPage`（AuthController 里专给前端包的兼容接口） |
| 开关 `1=启用`，单选 `1=男` | 库里 `0=正常`，`male/female` 字符串 | 同上，来回都要翻（提交时记得翻回去） |
| 路由表 `RowRoute[]`（`dir/page`，`pid:0` 表顶级） | `sys_menu` 全表映射，按钮权限行要过滤掉 | 后端 `GET /getUserRoutes` + 前端 `createRoutes` 过滤 |
| 角色下拉 `{label, value}` | `GET /role/options`（无权限码，登录即用） | 直接对上，`n-select` 的 `label-field/value-field` 别写错 |
| 字典 `{label, value}` / 类型 `{label, code}` | `GET /dict/list?code=` | 同上 |

## 第 9 章 调试手册：三板斧 + 报错对查表

1. **Swagger**：http://localhost:3001/api-docs，右上角 Authorize 贴 `Bearer {token}`，直接发请求，不用猜。
2. **日志**：后端黑窗口实时刷 `[Nova] ... [RoutesResolver]`（路由表，启动时看一遍有没有你的新接口）、`[HTTP] AuthController -> login -> [POST]/login`（每次请求一行，报错带堆栈）。
3. **直连数据源**：psql 查表（`select id,username,status from sys_user;` 注意列名是下划线！）、`redis-cli keys 'user_token:*'` 看会话在不在。

| 报错 | 先查什么 |
|---|---|
| `未登录`（401） | 请求头有没有 `Authorization: Bearer xxx`（alova 自动加，swagger 里要手工贴） |
| `用户会话已过期或不存在` | Redis 里会话键在不在：刚登录完就报 → 接口是不是误贴了 `@Public()`（见 3.4 节血泪教训）；登录很久报 → 正常过期，重登 |
| `权限不足` | 查该用户角色的 `perms`（`sys_menu` 表）+ 是否走了 admin 旁路；新接口先确认权限码字符串和菜单里配的一字不差 |
| `用户不存在` / `密码错误` | 前端默认账号是 `super`，库里只有 `admin`；新用户密码看是不是经过 `@BeforeInsert` 加密了（service 里**不要**再加一次，会双重哈希） |
| `重复键违反唯一约束 pk_*` | 导过种子数据没校准序列，`setval` 那一条（见 5.3 节） |
| 接口 404 | ① Module imports 登记没 ② Controller 路径拼错没 ③ 看启动日志路由表有没有这行 |

## 附录 A：我们踩过的坑（都是真金白银交过的学费）

1. `@Public()` + `@RequirePermissions` 贴一起 → 所有请求会话为空（POST /user 瘫痪）。
2. Entity `@BeforeInsert` 已加密，Service 再加密一次 → 新用户永远登不上（双重哈希）。
3. 种子数据带固定 id → 序列错位 → 新建主键冲突（六张表都要 `setval`）。
4. 登录默认账号 `super`，库里只有 `admin`（前端问题，但每次都在后端日志里现形）。
5. 目录路由给了 component → 子页面全被占位页吞掉（前端 `createRoutes`，目录必须保持无组件）。
6. `VITE_ROUTE_LOAD_MODE` 改完要重启 Vite（`.env` 是启动时读的，HMR 救不了）。
7. PowerShell 写文件默认 CRLF，仓库要 LF（prettier 满屏 `Delete ␍`）——编辑器开 format on save + 留意 `.editorconfig`。
